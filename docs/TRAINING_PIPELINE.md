# 정답 → 재학습 → 모델 배포 설계 (TODO)

2026-11-25 · 초안 · 대상: 앱·파이·학습 담당

앱에서 사용자가 표시한 정답(오탐 고치기 포함)을 모아 판정 모델을 다시 학습하고, 새 모델을 파이에 내려보내는 흐름이다.
지금은 정답이 파이 DB에 저장만 되고 학습에는 쓰이지 않는다.
같은 서버로 보내는 백그라운드 알림(푸시)도 TODO 5에 함께 둔다.

## 지금 있는 것

| 위치                                                  | 하는 일                                                                                                                        |
| ----------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------ |
| 앱 상세 화면                                          | "맞아요" / "다른 상황이에요" → `POST /api/events/{id}/label`                                                                   |
| 파이 `store.py`                                       | 이벤트 JSON의 `label`에 정답 저장 (DB). 최종 판정마다 그 사람의 레이더 행을 `~/doorradar-data/rows/<날짜>/<id>.json.gz`에 저장 |
| 파이 `server.py`                                      | 켜질 때 `config.toml`의 `model`(`situation_trees_real.pkl`) 한 번 읽음. `/api/info`의 `model`, `model_version`으로 알림        |
| PC `sg-radar-tools/tools/behavior/train_situation.py` | 정답 표 `labels.csv`(녹화 파일 `.pcr` 또는 `_tracks_raw.csv` + 상황 + train/test)로 상황 트리 학습 → `.pkl`                    |
| PC `pi_server/deploy.ps1`                             | 코드와 `models/*.pkl`을 파이에 복사                                                                                            |

없는 것: 정답 붙은 이벤트를 학습 데이터로 내보내기, 업로드, 서버 학습, 자동 배포.

## 목표 흐름

```
앱 ──정답──▶ 파이 DB
               │ (1) 정답 붙은 이벤트 + 레이더 행만 업로드 (사진 제외)
               ▼
           학습 서버 ── (2) 모아서 다시 학습 ── (3) 고정 테스트로 검증 ── 통과하면 "최신 모델"로 공개
               ▲
               │ (4) 파이가 3일마다 최신 버전 확인 → 새 버전이면 받아서 교체
             파이
```

## 정한 것

- **올리는 것**: 정답(`label`)이 붙은 이벤트 요약 + 그 이벤트의 `rows/*.json.gz`. DB 통째나 사진은 올리지 않는다.
- **정답 없는 이벤트는 "맞음"으로 보지 않는다.** 사용자가 안 본 것일 수 있다.
- **"맞아요"도 정답으로 쓴다.** 오탐만 모으면 데이터가 한쪽으로 쏠린다.
- **모델은 파이가 받아 간다(pull).** 파이는 집 공유기 안이라 서버가 먼저 붙기 어렵다.
- **확인 주기 3일.** 확인 요청은 작지만, 모델 교체가 잦으면 판정이 자주 바뀌어 비교·디버깅이 어렵다. 3일이면 그 사이 정답도 충분히 쌓인다.
  - 켜질 때 한 번 + 이후 3일마다. 여러 대면 시각을 조금씩 흩는다.
  - 급할 때를 위해 수동 확인(명령 또는 API)도 둔다.
  - 문 앞에 사람이 없을 때 교체한다(진행 중 판정이 끊기지 않게).
- **모델 단위: 지금은 하나.** 실험 환경이 한 곳뿐이라 공통 모델과 집별 모델을 구분해 검증할 수 없다. 제품 단계는 아래 "집마다 따로 학습하면"을 참고.

## 집마다 따로 학습하면 (제품 단계 메모)

**좋은 점**

- 집 구조에 맞는다. 문 위치, 복도 폭, 이웃이 지나가는 길, 택배 놓는 자리가 집마다 다르다.
- 데이터가 그 집 안에서만 쓰여 개인정보 설명이 쉽다.

**어려운 점**

- **데이터가 적다.** 한 집에서 나오는 정답은 하루 몇 개라, 특히 이상 상황(배회·반복 접근)은 몇 달에 몇 개다. 트리가 그 몇 개에 과하게 맞춰진다.
- **새 집은 데이터가 없다.** 처음엔 어차피 공통 모델이 필요하다.
- **집별 검증이 어렵다.** 집마다 테스트 세트를 따로 만들 수 없어서, 새 모델이 나빠졌는지 판단하기 어렵다.
- **운영 부담.** 모델이 집 수만큼 생겨 버전 관리, 되돌리기, 문제 추적이 늘어난다.
- **정답 잡음이 그대로 들어간다.** 가족 한 명이 잘못 누른 정답이 그 집 모델을 바로 흔든다.

**현실적인 형태**

- 공통 모델은 모든 집 데이터로 서버에서 학습한다(기본).
- 집별로는 모델 대신 **보정 값**만 맞춘다. 측정 영역(`region`), 촬영 기준(`camera_prob`, `camera_hold_s`), 장시간 체류 기준 시간처럼 이미 설정으로 있는 값이다.
- 한 집에 정답이 충분히 쌓이면(상황별 N개 이상) 그 집만 공통 모델 위에 덧붙여 학습하고, 공통 모델보다 나을 때만 쓴다.

우리 실험은 한 환경뿐이라 이 차이를 검증할 수 없다. 발표 때는 "한 환경 실험, 제품에서는 공통 모델 + 집별 보정"으로 범위를 밝힌다.
